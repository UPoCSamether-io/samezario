# 『サメザリオ』ゲーム基本仕様書

- **ステータス**: 現行4ロケ地版の統合仕様
- **更新日**: 2026-08-16
- **対象**: U☆PoC審査デモおよび現行Samezario

この文書は、旧 `UPoC_Samether.io` の8エリア構想をそのまま移植せず、現行ゲームの
4ロケ地・Canvas2D・Node.js構成へ統合するための基準を定める。

実装済みのゲーム挙動は現行コードを正とし、写真解放など未実装部分は本書を目標仕様とする。
旧リポジトリの設計資料は判断材料として参照できるが、本書と競合する場合は本書を優先する。

---

## 1. 概要

- **タイトル**: サメザリオ / Samezario
- **コンセプト**: 映画の町・調布を舞台に、調布モチーフのサメで遊ぶ `.io` 系オンラインアクション。ゲームプレイと現地訪問を組み合わせ、遊びながら調布の歴史や魅力に触れる地域連携エンタメ。
- **プラットフォーム**: PC・スマートフォンのモダンブラウザ
- **操作**: PCはマウス・キーボード、スマートフォンは仮想スティックと画面ボタン
- **目的**: 調布の魅力を発信し、ゲームから現地訪問、現地訪問から新しいロケ地でのプレイへ循環させる。

---

## 2. コアゲーム

### 2.1 ゲームループ

1. タイトルからロケ地を選ぶ。
2. 未解放ロケ地では、解放スポットと撮影条件を確認する。
3. 解放済みロケ地では、サメを選んでオンライン対戦へ参加する。
4. 餌を食べて成長し、ダッシュ・航跡・固有スキルを使って生存と順位を競う。
5. カットされたら、到達サイズ・撃破数・生存時間・調布Tipsを確認する。

オンラインサーバーへ接続できない場合は、同じゲームルールのボット戦へ切り替える。

### 2.2 操作と死亡条件

- **移動**: PCはカーソル方向、スマートフォンは仮想スティック方向へ旋回する。
- **ダッシュ**: 左クリック・Space・画面のDASHボタン。スタミナを消費して加速する。
- **航跡**: ダッシュ中に一定時間残る。他のサメが触れるとカットされる。
- **固有スキル**: E・Shift・画面のスキルボタン。サメごとに効果とクールダウンが異なる。
- **死亡**: 外壁、他のサメの胴体、他のサメの航跡へ頭から接触するとカットされる。
- **サイズ差**: 衝突の勝敗には使わない。接触した側がカットされる。

### 2.3 キャラクター

MVPでは5種類を最初から選択できる。

| サメ | 特徴 | 固有スキル |
| --- | --- | --- |
| 映画サメ | 標準バランス型 | スポットライト: 前方の敵をスローダウン |
| 妖怪サメ | 旋回性能が高く、速度はやや遅い | すり抜け: 一時的に胴体・壁を透過 |
| 多摩川サメ | 高速だが旋回と成長が控えめ | 急流ブースト: コストなしの直線加速 |
| 深大寺サメ | 成長効率が高い | そばガード: 衝突死を1回無効化 |
| 飛行機サメ | ダッシュ効率が高い | 旋回飛行: 周囲の餌を吸引 |

## 3. 現行4ロケ地

### 3.1 採用方針

プレイエリアは次の4ロケ地で固定する。旧構想の京王多摩川・国領・柴崎・つつじヶ丘・
西調布・飛田給を独立ステージにする8エリア案は採用しない。

現行 `src/data.js` のSVG輪郭は、ロケ地選択画面の形とゲーム内の外周を兼ねる。
写真解放の導入時も、MapLibreや駅単位のエリアへ置き換えない。

### 3.2 ロケ地と解放条件

| ID | ロケ地 | 初期状態 | 解放・達成スポット | 緯度・経度 | ジオフェンス | 撮影ガイド | 前提条件 |
| --- | --- | --- | --- | --- | ---: | --- | --- |
| `chofu` | 調布駅・布田 | 初期解放 | 布多天神社（ボーナススポット。ロケ地解放には使わない） | 35.6553, 139.5439 | 150m | 参道正面から、鳥居全体が入るように撮影 | なし |
| `jindaiji` | 深大寺 | 未解放 | 深大寺 山門 | 35.6656, 139.5497 | 150m | 参道から、山門全体が入るように撮影 | `chofu` 解放済み |
| `tamagawa` | 多摩川 | 未解放 | 調布市郷土博物館 | 35.6461, 139.5395 | 150m | 正面入口から、建物と館名板が入るように撮影 | `chofu` 解放済み |
| `airport` | 調布飛行場 | 未解放 | 味の素スタジアム前モニュメント | 35.6644, 139.5271 | 200m | 正面から、モニュメント全体が入るように撮影 | `chofu` 解放済み |

3つの未解放ロケ地に相互の順序は設けない。プレイヤーは調布駅・布田から、興味や移動経路に
合わせて好きなロケ地を選べる。全ロケ地踏破を将来の達成条件に使うことはできるが、
MVPでは深大寺をラスボスとして封印する進行にはしない。

上表を初期マスタ値とする。現地確認や連携先との合意によってスポット名・座標・撮影可否を
変更する場合も4ロケ地のIDは維持し、スポットマスタを版管理して差し替える。

### 3.3 ロック状態

ロック状態はロケ地マスタへ固定値として保存しない。マスタとユーザー進捗から毎回導出する。

- `unlocked`: 初期解放、または `UserProgress.unlockedMapIds` に含まれる。
- `unlockable`: 未解放で、`requires` の全ロケ地が解放済み。
- `locked`: 前提ロケ地が未解放。

現在の4ロケ地では、初回に `chofu` が `unlocked`、残り3件が `unlockable` になる。

## 4. 現地写真によるロケ地解放

### 4.1 基本フロー

1. 未解放ロケ地を選び、スポット名・お手本・撮影ガイドを確認する。
2. スマートフォンの背面カメラ、または端末内の写真を選ぶ。
3. 写真を見た目の向きへ正規化し、長辺1280px程度のJPEGへ縮小する。
4. ボタン操作に続けて現在地を1回取得する。常時トラッキングはしない。
5. 写真・スポットID・緯度経度・匿名トークンを `POST /api/verify` へ送る。
6. サーバーがジオフェンスと画像類似度を判定する。
7. 成功時はサーバーが進捗を更新し、更新後の進捗全体を返す。
8. クライアントは進捗を丸ごと置換し、解放演出・歴史解説・赤ピンを表示する。

### 4.2 判定方針

判定は「位置は厳密に、画像はゆるく」の二段構えとする。

- **位置**: Haversine距離がスポットごとのジオフェンス以内かを先に判定する。
- **画像**: 同じ正規化処理を通した基準写真とdHash等の知覚ハッシュを比較する。
- **しきい値**: 現地の正例・負例でスポットごとに調整する。
- **重複**: 同じスポットの再成功で解放・報酬を二重付与しない。

アルゴリズムは実測により変更できるが、APIレスポンスと進捗更新の経路は変えない。
SSIM・特徴点・外部画像認識サービスを追加する場合も、サーバー側の判定アダプターとして扱う。

### 4.3 デモモード

審査会場が調布市外の場合に備え、`?demo=1` の画面導線を用意する。ただし、クエリだけで本番の
判定を迂回させない。サーバー側の `ALLOW_DEMO_VERIFY=1` 等が同時に有効な環境でのみ成功させる。
画面にはデモ判定であることを表示する。

### 4.4 プライバシーと制限

- 写真は照合後すぐ破棄し、MVPでは保存しない。
- 位置情報は距離判定だけに使い、移動履歴を保存しない。
- JPEG/PNGのみ、受信上限5MBとする。
- トークン単位で照合試行をレート制限する。
- 参照画像・参照ハッシュ・しきい値をクライアントへ配信しない。
- 権限拒否時は、端末設定から再許可する方法を案内する。

## 5. データ構造と責務

### 5.1 公開マスタ

ブラウザとサーバーの両方が読める。不変のコンテンツ情報だけを持つ。

```text
MapMaster
  id, name, en
  path, label, color, size, water
  blurb, lore
  defaultUnlocked
  requires[]
  unlockSpotId

SpotMaster
  id, mapId, name
  location { lat, lon }
  geofenceM
  sampleImageUrl, angleGuide, description
```

`unlocked` のようなユーザーごとに変わる値、参照ハッシュ、照合しきい値は置かない。

### 5.2 サーバー専用照合情報

```text
SpotVerifySecret
  spotId
  refImages[]
  referenceHashes[]
  algorithm
  threshold
```

公開ディレクトリとクライアントバンドルへ含めない。基準写真の撮影条件としきい値変更履歴も
サーバー側で管理する。

### 5.3 ユーザー進捗

```text
UserProgress
  version
  token
  unlockedMapIds[]
  clearedSpots { spotId: { clearedAt, matchScore } }
  updatedAt
```

- 進捗の正はサーバー。
- クライアントのlocalStorageは匿名トークンと最後に受信した進捗のキャッシュ。
- 更新は、サーバーが作った完全な `UserProgress` でクライアントを置換する1経路に限定する。
- 保存データを読めない場合は初期状態へ戻し、アプリの起動を妨げない。

### 5.4 オンライン参加制御

WebSocketのjoinにはロケ地IDと匿名トークンを含める。サーバーは進捗を確認し、未解放・不明な
ロケ地への参加を `join_rejected` 相当の理由付きで拒否する。不明なIDを調布へ黙って置換しない。

## 6. 学習・歴史コンテンツ

プレイ操作を妨げない場所で提示する。

1. ロケ地解放時に、達成スポットと周辺の歴史・文化を表示する。
2. リザルト画面で調布Tipsをランダム表示する。
3. サメ図鑑に、各サメのモチーフとなった場所・文化の史実を掲載する。

キャラクターの冗談を含む紹介文と史実は別フィールドで管理し、混在させない。

## 7. 現行技術構成

- **クライアント**: Vite + JavaScript + Canvas2D + Tailwind CSS v4
- **ゲームロジック**: `src/sim.js` をブラウザとNode.jsサーバーで共有
- **サーバー**: Node.js HTTP + `ws`
- **オンライン対戦**: ロケ地別ルーム、サーバー権威、30Hzシミュレーション、15Hz配信
- **進捗・照合API**: 同じNode.jsサーバーへ追加する
- **オフライン時**: 盤面を引き継いでボット戦へ移行する

ゲーム状態と解放進捗の正はサーバーとする。ブラウザ側のゲームシミュレーションは入力遅延を
隠すための予測であり、サーバーのスナップショットで補正される。

## 8. 旧UPoC構想からの採否

| 旧構想の要素 | 判断 | 現行での扱い |
| --- | --- | --- |
| 現地写真でエリア解放 | 採用 | 4ロケ地の解放条件として実装 |
| ジオフェンス＋知覚ハッシュ | 採用 | Node.jsの `/api/verify` で判定 |
| 公開マスタと照合秘密の分離 | 採用 | `SpotMaster` / `SpotVerifySecret` に分離 |
| サーバー権威の進捗 | 採用 | 匿名トークンと永続Storeで管理 |
| 解放演出・歴史解説・赤ピン | 採用 | 現行SVGマップとUIへ統合 |
| 8エリアの駅別進行 | 不採用 | 現行4ロケ地を維持 |
| 深大寺を全エリア踏破後のボスにする | MVPでは不採用 | 深大寺は調布から直接解放可能 |
| MapLibre / Amazon Location | 不採用 | 現行SVGマップを維持 |
| Phaser + TypeScriptへの移行 | 不採用 | 現行Canvas2D + JavaScriptを維持 |
| Go + Redis + ECS/Terraformへの移行 | 不採用 | 現行Node.js構成へ必要な機能だけ追加 |
| Reactモックの取り込み | 不採用 | デザイン参考に限定 |
| `?demo=1` | 条件付き採用 | サーバー環境設定との二重条件で有効化 |
| SNSシェア報酬 | 将来検討 | ポイントの用途が決まるまで共有機能のみ |

## 9. 実装順序

1. ロケ地・スポットマスタとロック状態導出
2. 匿名トークンとサーバー進捗Store
3. 撮影・画像正規化・位置取得UI
4. `/api/verify` と進捗更新
5. 制限付きデモモード
6. WebSocket join時の解放検証
7. 解放演出・歴史表示・実機テスト

各段階で `npm test` と `npm run build` を実行し、既存の対戦・ボット戦を壊していないことを確認する。
