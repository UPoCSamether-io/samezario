## 実装方針

### 上限値（すべて環境変数で変えられる）

| 環境変数 | 既定（案） | 意味 |
| --- | --- | --- |
| `WS_MAX_ROOMS` | 8 | 総部屋数。README「必要なCPU」の実測（0.5 CPU で 40人＝5部屋が 14.5/s）と t3.micro のバースト 2 vCPU から。 |
| `WS_MAX_PER_IP` | 0（無制限） | IP ごとの同時接続数。**会場の Wi-Fi は全員が同じグローバル IP（NAT）になる**ので、既定で絞ると会場の全員が締め出される。要判断。 |
| `WS_MAX_PAYLOAD` | 4096 | 1メッセージの最大バイト数。クライアントが送る最大は `join`（名前10文字）で 200 バイト未満。 |
| `WS_IN_RATE` | 40 | 1接続あたり毎秒受け付けるメッセージ数（平均）。クライアントは 20Hz（`game.js` L1107）。 |
| `WS_IN_BURST` | 80 | 一度に溜められる数。超えた分は**黙って捨てる**。 |
| `WS_IN_KILL` | 400 | 1秒にこれを超えて送ってくる線は切る（壊れたクライアント・悪意）。 |
| `TRUST_PROXY` | 0 | 1 なら IP を `X-Forwarded-For` の先頭から取る。本番は Caddy の後ろ（`docs/deploy-ec2.md` L7）なので、**これを 1 にしないと全員が 127.0.0.1 に見える**。 |

- 読むのは `attach()` の中（既存の `WS_DEAD_MS` L165 と同じ）。モジュール読み込み時に読むと、テストで環境変数を変えて `attach` し直せない。

### 総部屋数
- `joinRoom` で、空きのある同じマップの部屋が無く、かつ `rooms.size >= MAX_ROOMS` なら新しい部屋を立てずに `null`。
- 「既存の部屋へ寄せる」は**同じマップの部屋**にしかできない（マップが違えば盤面が違う）。同じマップの部屋が満席（`CAP = 14`）のときに押し込むと、`world.addPlayer` はボットが残っていなければ足すだけ（`sim.js` L503〜509）で 15匹以上になり、密度が変わる（L498〜501 のコメント）。→ 押し込まない。
- 断るときは `send(ws, { t: 'busy' })` → `ws.close(1013)`（Try Again Later）。

### クライアント側は変えない
- `net.js` の `connect()` は hello の前に閉じられると `onclose → fail()` で reject し、`main.js` の `play()` が `catch { net = null }`（L1300）でソロに落ちる。つまり**混雑時は黙ってソロ**になり、既存の「サーバに繋がらなければ黙ってボットだけの部屋」（README「オンライン対戦」）と同じ体験になる。
- 「混雑しているのでソロで撮影中」と知らせたい場合は `net.js` / `main.js` の変更になる（要判断。入れるなら別 PR）。

### IP ごとの同時接続
- `server.on('upgrade')`（L154）で IP を決め、`Map<ip, count>` を数える。超えたら `socket.write('HTTP/1.1 429 Too Many Requests\r\n\r\n'); socket.destroy()`。`ws.on('close')` で減らす（0 になったら Map から消す ＝ メモリを溜めない）。
- IP は `TRUST_PROXY=1` のとき `req.headers['x-forwarded-for']` の先頭、それ以外は `req.socket.remoteAddress`。

### 受信頻度
- `wire()` の `message` の先頭で、接続ごとのトークンバケツ（`ws.tokens`, `ws.tokT`）を `Date.now()` で補充。0 なら捨てる（`JSON.parse` もしない ＝ CPU を守る）。
- 1秒窓で `WS_IN_KILL` を超えたら `ws.terminate()`。
- `ws.seen` の更新（L104、無言で切る仕組み）は捨てたメッセージでも行う（送ってきてはいるので）。

### maxPayload
- `new WebSocketServer({ maxPayload })` を 4096 に。超えると ws ライブラリが 1009 で閉じる。

### 負荷測定（余力）
- `scripts/loadtest.mjs --clients 40 --seconds 20` を本番相当（README の docker `--cpus=0.5`、または EC2 実機）で流し、配信レート・部屋数・`busy` で断られた数を `docs/final/STATUS.md` に残す（リポジトリのルートに STATUS.md は無いので docs/final に置く提案。要判断）。
- loadtest は1台から全接続を張るので、`WS_MAX_PER_IP` を絞った状態では自分が締め出される。測定時は既定（0）で。`.github/workflows/load-test.yml` も同じ。

## リスク

- **sim.js 同期**: 触らない。
- **描画負荷**: 無関係。
- **会場の NAT**: 上記のとおり。IP 上限は既定で無効、本番でも会場の人数より十分大きく（例: 64）。
- **Caddy の後ろ**: `TRUST_PROXY` を本番の systemd ユニット（`scripts/ec2-deploy.sh`）で 1 にしないと IP 上限が全員一括になる。逆に Caddy を通らない直結で 1 にすると、`X-Forwarded-For` を偽装して上限をすり抜けられる（直結では 0 のまま）。
- **ソロへ落ちる体験**: 断られた人は対戦にならない。部屋数の上限を低くしすぎると、会場の大半がソロになる。発表の前に loadtest で上限を決める。
- **衝突**: `server/` だけなので他の issue と並列可。#3a は sim.js を変えるのでサーバの再デプロイが要る —— デプロイを1回にまとめるなら #3a と #10 を同じ便で出す。`README.md` は #11 も触る（別の節なので merge は容易）。

## 要判断

1. `WS_MAX_ROOMS` の既定（推奨 8）と、本番での値。
2. IP ごとの上限を有効にするか（会場 NAT のため推奨: 無効、または 64 程度）。
3. 混雑で断られた人に「混雑のためソロ」と知らせるか（クライアントの変更が要る）。
4. 負荷測定の結果を置く場所（`docs/final/STATUS.md` でよいか）。
