# #3a [P0] 開始直後に理不尽に死なない —— 原因の修正（湧き位置・無敵の同期・盤面時計）

**触るファイル**: `src/sim.js` / `src/sim.test.mjs` / `src/game.js`（`frame()` だけ）
**触らない**: `src/main.js` / `index.html` / `src/style.css` / `server/index.mjs`（ただし sim.js を変えるので**サーバの再デプロイが要る**）

#3 は「原因の修正（3a）」と「開始時の演出（3b：カメラを寄せる・目印）」に分ける。3a → 3b の順。

## 目的

多摩川で湧いた直後に「外壁に接触」で死ぬ事故と、TIME / 生存時間が 0:00 のまま進まない不具合をなくす。

---

## 調査結果（原因）

### A. 「外壁に接触」で開始数秒で死ぬ

コードと実測（`createWorld` を Node で回した。スクリプトは scratchpad、リポジトリには置いていない）から、原因は3つ重なっている。

1. **湧き位置が壁際になりうる**。`makeShark()`（`sim.js` L459〜）は `arena.spot()`（L151、外接矩形からの棄却サンプリング）をそのまま使い、壁からの距離を見ていない。向き `angle` も `rand(0, TAU)` で、壁を向いて湧く。
   実測（各マップ 300 回湧かせた、壁までの距離）:

   | マップ | 10%点 | 中央値 | 300px 未満の割合 |
   | --- | ---: | ---: | ---: |
   | chofu | 85px | 543px | 28% |
   | **tamagawa** | **70px** | **379px** | **41%** |
   | airport | 110px | 541px | 29% |
   | sengawa | 66px | 527px | 35% |

   多摩川は通路の中央値が 768px と一番細い（`docs/stage_design_plan.md` §4.3）ので、壁際に湧く率が最も高い。

2. **無敵中は壁に「貼り付いた」まま時間が過ぎ、切れた瞬間に死ぬ**。無敵中の壁は押し戻し（`sim.js` L1099〜1107: 直前の位置へ戻して向きだけ変える）だが、多摩川では**流れ（`windAt`）が毎ティック向きと無関係に体を押す**（L1092〜1094）。壁の向こうへ流れている場所では、無敵の3秒間ずっと壁に押し付けられ、`iframe` が 0 になった最初のティックで `die(s, null)`（L1110）。
   実測（操作なし＝湧いた向きのまま、各 300 回）: 12秒以内の外壁死は chofu 50% / **tamagawa 79%** / airport 50% / sengawa 48%。**3.0〜3.5秒（無敵が切れた直後）の外壁死**は chofu 16% / **tamagawa 25%** / airport 19% / sengawa 18%。
   「1秒で反応して壁から離れる向きへ舵を切る」操作にしても、多摩川だけ 400 回中 1 回、**ちょうど 3.0秒・流れの帯**で外壁死した（他マップは 0）。

3. **オンラインでは、自機の無敵はクライアントだけが数えていて、サーバの値で直らない**。`applySnapshot()` の `s.iframe = flags & 16 ? 0.25 : 0`（L1267）は `s.nid !== me` の枝の中にしかない。自機の `iframe` は `game.js` の `addPlayer` 時点（L128）の 3秒から**手元の `step()` だけ**で減る。サーバ側は join（`server/index.mjs` L113）で 3秒を数え始めるので、その時点で既に「サーバは無敵が切れているのに、画面では点滅（`drawShark` L473）していて、手元の予測は壁で押し戻している」ずれが生まれる。下の B が起きるとこのずれは秒単位に広がる。

### B. 多摩川で TIME が 0:00 のまま・生存時間 0:00

- HUD の TIME もリザルトの生存時間も `world.elapsed`（`game.js` L1127 / L287）。`elapsed` は `world.step(dt)` の中でしか増えない（`sim.js` L1014）。
- `frame()` の dt は **1フレーム 0.05秒で頭打ち**（`game.js` L1094 `Math.min(0.05, t - last)`）。fps が 20 を割ると、**盤面の時計が実時間より遅れる**。4fps なら実時間 1秒で盤面は 0.2秒しか進まない。
- 一方サーバは固定 dt で実時間どおり回り（`server/index.mjs` L60〜68）、盤面の正もサーバなので、画面上のサメはスナップショットのワープ（`applySnapshot` の d ≥ 120 で即時スナップ L1291〜1296）で実時間どおり動いて見える。**動いているのに TIME だけ進まない**状態になる。
- **再現できた**: playwright（headless Chromium、844×390・isMobile、dev サーバ相乗りの /ws に接続）で CPU を 6倍に絞ると多摩川は 2〜4fps になり、**実時間 12秒後に TIME = 0:02、自機の `iframe` は手元でまだ 0.30 残っていた**（サーバではとうに切れている）。絞らない 1280×720 では TIME は正しく進んだ。
- 同じ絞り（4倍）で fps を比べると chofu 19 / airport 10〜12 / tamagawa 9〜10。headless はソフトウェア描画なので実機の差は測り直しが要るが、**ギミックのある2マップは描画が重く、多摩川は最も重い側**。ユーザーテストの端末で多摩川だけ fps が大きく落ちた、が最有力の仮説。
- **A と B はつながっている**: fps が落ちると、手元の無敵（点滅）が実時間より長く残る → サーバでは無敵が切れて壁で死ぬ → 「無敵中なのに外壁で死んだ」に見える。

## 実装方針

### 湧き位置（sim.js）
- 定数 `SPAWN_CLEAR = 450`（px、壁までの距離）を `sim.js` 冒頭の定数群に置き、根拠をコメントで残す（「初期の素の速さ 172px/s × 無敵 3秒 ≒ 516px より少し内側。これ以上取ると多摩川の河川敷で候補が尽きる」）。
- `safeSpot`: `arena.spot()` を最大 240 回引き、各点を `min(edgeDist, SPAWN_CLEAR) + (凪の帯なら +SPAWN_CLEAR)` で採点して最良を返す。打ち切りがあるので必ず返る（最後の砦は従来の `spot()`）。
  - **多摩川は流れの無い帯（河川敷）に出す**: 「凪」は `gimmick.windAt(x, y, 0)` が `NO_WIND`（速度 0）であること。`makeGimmick` は `createWorld` 内で `arena` の直後に作られている（L338）ので `makeShark` から参照できる。データの数値（`data.js` の `bands`）は触らない。
  - 実測: 多摩川で「凪 かつ 壁から 400px 以上」の点は内側の 6.7%。240 回引けば外れる確率は 1e-7 未満。
- `openHeading`: 16方向へ 60px 刻みで最大 1200px まで `inside()` を撃ち、いちばん遠くまで内側が続く向きを返す。
- 計算は湧くときに1回だけ（`edgeDist` は頂点 26〜64 個の総当たりで、240 回でも 1ms 未満）。tick には載らない。
- 乱数は `Math.random` のまま（サーバが正なので、クライアントと一致させる必要は無い。クライアントの自機は `full` 到着時にサーバの位置へワープする）。

### 自機の無敵の同期（sim.js）
- `applySnapshot` の自機の枝で `if (!(flags & 16)) s.iframe = 0;` を足す。逆（サーバが無敵なのに手元が 0）は起きないので延ばす処理は不要。
- L1205〜1210 のコメント「自分の向き・ダッシュ・スキル演出はローカルの値を残す（押した瞬間から反応させたい）」の対象は**操作**であって、無敵は操作ではなくサーバが決める効果。`slow` / `rapid` を自機にも当てている L1269〜1274 のコメントと同じ理屈なので、そこに並べて書く。

### 盤面の時計（game.js `frame()`）
- `server/index.mjs` の `makeRoom` のコメント（L52〜56）「詰まったぶんを dt に乗せると、復帰した1ティックでサメが体半分ぶん進んで壁や相手をすり抜ける」が、0.05秒で切っている理由と同じ。**1回の dt は 0.05 のまま、回数で追いつく**:
  ```
  let acc = min(t - last, 0.25)        // タブ復帰などの大穴は 0.25 秒で捨てる
  while (acc > 0) { step(min(acc, 0.05)); acc -= 0.05 }
  ```
  4fps（1フレーム 0.25秒）まではこれで実時間に追いつく。それ以下は従来どおり遅れる（死のスパイラル防止）。
- `step()` を複数回呼んでも、カメラ・エフェクト・ダッシュ音の立ち上がり（L413〜417）は dt に比例して進むので問題ない。`net.send`（L1105〜1117）と HUD（L1119〜）は1フレーム1回のまま。
- TIME は `world.elapsed` のまま（盤面の時計で出す。実時計 `performance.now()` に変えると、ポーズ中も進んでしまう）。

## リスク

- **sim.js のサーバ/クライアント同期**: 湧き位置はサーバだけが決めて `full` で配るので同期は崩れない。`applySnapshot` の変更は自機の `iframe` を縮めるだけ。サーバを先に、クライアントを後にデプロイしても（逆でも）壊れない。**ただし湧き位置の改善はサーバを再デプロイするまで本番に出ない**。
- **棄却サンプリングのコスト**: 湧くたびに最大 240 × 64 頂点。人のサメの湧き（入室時）だけなので、30Hz の tick には影響しない。
- **描画負荷**: dt を刻むと低 fps 端末で `step()` が1フレーム最大5回になる。`world.step` は 14匹で 0.1〜0.5ms（README「必要なCPU」）なので、描画（数十 ms）に比べて小さい。描画そのものが重い問題は #7（多摩川の描き直し）で扱う —— #7 の受け入れ条件に fps 比較を入れてある。
- **既存テストの乱数依存**: §16 などは `addPlayer` で湧いた位置を `place()` で置き直しているか要確認。置き直していないテストは湧き位置が変わると結果が変わる。
- **衝突**: `game.js` の `frame()` は #4（ヒットストップ）と #5（順位表）も触る。3a → 4 → 5 の順に直列。`sim.js` を触るのはこの issue だけ（#5 の王冠ボーナスを入れる場合を除く）。

## 要判断

1. `SPAWN_CLEAR`（壁から何 px 離すか）。推奨 450px。
2. 多摩川以外でも「ギミックの効かない場所」に湧かせるか（飛行場の滑走路の帯を避ける等）。推奨: 多摩川だけ。
3. 無敵 3秒（`iframe: 3`、L484）そのものは変えない方針でよいか。
